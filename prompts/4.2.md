# Bouée §4.2 — Équipes d'agents (3 features parallèles)

> À utiliser **uniquement** si tu es bloqué après 15 minutes. Essaie d'abord de formuler ton propre prompt.

## Contexte

§4.2 livre **3 features indépendantes en parallèle** depuis une seule session principale, via 3 sous-agents `general-purpose` isolés dans des **worktrees Git** distincts. Chaque feature touche un domaine séparé (UI / perf / backend) → aucun chevauchement de fichiers → merge garanti sans conflit.

Pré-conditions livrées en amont :
- `/quality-gate` (§4.1) opérationnel — chaque sous-agent l'invoque avant remontée.
- 3 contrats `docs/features/<feature>/{prd.md, design.md}` à écrire **avant** le dispatch (sans contrat clair, le sous-agent dérive).

Mode dégradé : si le dispatch parallèle natif (`isolation: worktree` + `run_in_background: true`) n'est pas disponible dans ton environnement, livre les 3 features séquentiellement dans la même session. Le résultat sur `solution` est identique.

## Mode dégradé séquentiel

Si pas de dispatch parallèle natif, livre les 3 features une par une dans la même session, dans cet ordre :
1. Cloud Patterns (schema d'abord, c'est le seul à toucher la persistance).
2. Speed Demon (le worker est isolé, peu de friction).
3. Glow Up (UI uniquement, dernier pour ne pas masquer une régression).

## Pièges

- **Ne pas supprimer `game_states`** — Cloud Patterns **étend** le schema, il ne le remplace pas. Vérifier que `repository.ts` (§3.3) tourne toujours.
- **Web Worker sous Next 16 / Turbopack** — le pattern `new Worker(new URL('./step.worker.ts', import.meta.url))` est supporté nativement. Garder le wrapper isomorphe : `typeof Worker === 'undefined'` (côté serveur, lors d'un render initial) → fallback synchrone vers `step()`.
- **Pas d'authentification réelle** — `anon_authors.token` est un cookie aléatoire généré côté client. Pas de hash, pas de session. C'est volontaire (cf. DESIGN §10).
- **Glow Up sans framework de theming** — pas de `next-themes`, pas de Context global. Un simple `useState` + classe sur `<html>` suffit pour la démo.
- **Mergerre dans l'ordre architectural** — si tu rencontres un conflit, c'est un bug du découpage : remonte-le, ne le résous pas en local.
- **Pas d'emoji** dans les agents et les docs — convention du repo formation.

## Régression `check:2.6` après dispatch Speed Demon

Le check §2.6 vérifie que `Board.tsx` (ou `use-simulator.ts`) avance encore d'une génération. Si tu remplaces complètement `tick(`/`step(` par `computeNextGrid(` (le wrapper Speed Demon), le check tombe à cause d'un identifiant qui ne contient ni `step` ni `tick`.

**Bonne pratique** : garde au moins une ligne avec `tick(current)` ou `tickWithRule(current, …)` côté `onStep` ou en branche de fallback de l'effet d'animation — c'est cohérent avec l'esprit Speed Demon (worker en chemin nominal, simulator en fallback synchrone) ET ça satisfait la régression.

```ts
// onStep — appel synchrone, le worker est réservé au running loop
const onStep = useCallback(
  () => setState((current) =>
    ruleName === CONWAY.name
      ? tick(current)
      : tickWithRule(current, getRule(ruleName))
  ),
  [ruleName],
);
```

> Côté check : depuis §3.3, la regex de `check:2.6` accepte tout identifiant `tick…(` ou `step…(` (donc `tickWithRule(`, `tickOnce(`, etc.). Mais elle ne reconnaîtra **pas** `computeNextGrid(` seul — d'où la consigne ci-dessus.
