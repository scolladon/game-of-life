Trois étapes : d'abord créer **trois agents** versionnés dans le repo (`.claude/agents/`), ensuite livrer une feature qui justifie leur usage (catalogue de seeds + sélecteur dans la grille), enfin déléguer la revue à deux d'entre eux. Comme pour les skills §2.7, les agents sont au scope projet — versionnés, partagés en équipe (miroir inverse du plugin §2.5).

Un agent, c'est un fichier `.claude/agents/<name>.md` avec un frontmatter (`name` + `description` + `tools` optionnel) et un corps qui sert de system prompt. Claude le déclenche automatiquement quand le contexte matche la `description`, ou explicitement via `@nom-agent`.

---

## Étape 1 — Créer les trois agents

Crée la structure suivante :

```
.claude/agents/
├── code-reviewer.md
├── architect-reviewer.md
└── test-writer.md
```

### `.claude/agents/code-reviewer.md`

- Frontmatter : `name: code-reviewer` + une `description` qui dit clairement *quand* Claude doit l'invoquer (ex. « Relit le diff courant et signale bugs, typage, immutabilité, oublis de test. À utiliser après chaque modification de code TypeScript ou React. »).
- `tools` : `Read, Grep, Glob, Bash` (lecture seule, pas d'écriture).
- Corps (system prompt) : périmètre = bugs probables, typage strict, immutabilité, naming, oublis de test. Format de rapport = liste classée par sévérité (CRITICAL / HIGH / MEDIUM / LOW). Pas de réécriture du code, uniquement des observations.

### `.claude/agents/architect-reviewer.md`

- Frontmatter : `name: architect-reviewer` + une `description` axée alignement avec `CLAUDE.md` (séparation `core/` / `components/` / `app/` / `lib/`, conventions de naming, frontières de couche).
- `tools` : `Read, Grep, Glob` (lecture seule).
- Corps : vérifie que la pureté de `core/` est respectée (zéro dépendance React/Next/DOM), que les composants restent présentationnels, que le naming suit la convention. Rapport = liste des écarts à `CLAUDE.md` + suggestion de relocalisation.

### `.claude/agents/test-writer.md`

- Frontmatter : `name: test-writer` + une `description` qui couvre les deux cas (test d'une fonction pure dans `core/` ou d'un module quelconque). Mentionne le skill `vitest-test` §2.7 dans la `description` ou le corps — *composition agent ↔ skill*.
- `tools` : `Read, Write, Edit, Bash` (écrit des tests, ne touche pas au code de prod).
- Corps : applique les conventions du skill `vitest-test` (AAA, `describe` + `it`, `sut`, helpers `O`/`_`). Refuse de modifier le SUT lui-même (un test = on teste l'existant, on ne le change pas).

## Étape 2 — Livrer la feature (un seul prompt à Claude)

Une fois les trois agents posés, copie-colle ce prompt :

> Livre une petite feature en deux temps.
>
> 1. Crée `src/core/patterns.ts` qui exporte un catalogue de seeds nommés du Game of Life :
>    - `BLINKER` (5×5), `BLOCK` (4×4), `TOAD` (6×6), `GLIDER` (6×6) — typés `Grid` (cf. `src/core/grid.ts`).
>    - Une fonction `getPattern(name: PatternName): Grid` qui retourne le seed correspondant (clone profond, immutabilité).
>    - Un type union `PatternName = 'blinker' | 'block' | 'toad' | 'glider'`.
>    - Une constante `PATTERN_NAMES: readonly PatternName[]` pour l'UI.
>    - Test co-localisé `src/core/patterns.test.ts` qui vérifie que `getPattern('blinker')` retourne une grille 5×5 avec exactement 3 cellules vivantes alignées, et que la fonction ne mute pas l'instance partagée. Demande à `@test-writer` d'écrire ce test.
>
> 2. Crée `src/components/PatternSelector.tsx` (client component, `'use client'`) :
>    - Props : `{ value: PatternName; onChange: (name: PatternName) => void }`.
>    - Rend un `<select>` Tailwind sobre listant les `PATTERN_NAMES`.
>    - Pas de logique métier — uniquement présentation + relai du callback.
>
> 3. Modifie `src/components/Board.tsx` :
>    - Ajoute un state local `pattern: PatternName` initialisé à `'blinker'`.
>    - Lorsque `pattern` change, recharge la grille via `getPattern(pattern)` et remet `generation` à 0.
>    - Monte `<PatternSelector value={pattern} onChange={...} />` à côté du bouton « Next ».
>
> Une fois ce code écrit, délègue à `@architect-reviewer` une revue de la séparation `core/` / `components/` (les seeds doivent vivre dans `core/`, pas dans le composant). Puis à `@code-reviewer` une revue du diff complet — typage, immutabilité, hooks React.

## Étape 3 — Vérifier

```bash
npm test               # 12 tests verts (11 existants + test patterns)
npm run check:2.8      # vert : agents + patterns + selector monté + générations resettées
npm run check          # 9/15 ✅ (1.4 → 2.8)
npm run dev            # menu déroulant : changer de seed remet la grille
```

Si `check:2.8` rouge :

- `Échec agent code-reviewer` / `architect-reviewer` / `test-writer` : fichier absent ou frontmatter `name`/`description` vide.
- `Échec patterns.ts` : module absent, ou seed/`getPattern`/`PATTERN_NAMES` manquant.
- `Échec PatternSelector` : composant absent, props mal typées, ou non monté dans `Board.tsx`.
- `Échec reset génération` : `Board.tsx` ne remet pas `generation` à 0 sur changement de pattern.
