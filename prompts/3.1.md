Trois étapes : conduire **une session optimisée tokens** sur le refactor d'un module, **tracer** la démarche dans un document Markdown, puis valider. La consigne pédagogique est de *vivre* la pression du contexte (`/context` qui grossit) et de *réagir* avec `/compact` au bon moment, pas de produire un refactor parfait du premier coup.

Une session "optim tokens", c'est trois mécaniques de base :
- **`/compact`** — Claude lit l'historique en cours, le résume en une note de synthèse, et redémarre le tour suivant avec cette note à la place de tout le détail. On garde le sens, on libère ~70-90 % du contexte. À déclencher quand on sent un ralentissement, une dérive (Claude oublie une consigne) ou avant un gros bloc de réflexion. **C'est ce qui produit la trace observable** : on note *ce qu'on a compacté* et *quand*.
- **`/clear`** — reset total du contexte. Utile entre deux sujets sans rapport (ex. fin d'une feature → démarrage d'un debug). Plus violent que `/compact` : on perd l'historique.
- **Sub-agents (`Task` tool)** — exécutent une recherche/audit dans **leur propre contexte isolé** et ne retournent que le résumé. Hyper utile pour grep/lecture massive (« audite toutes les usages de `setState` du repo ») : le bruit ne pollue pas la session principale.

Trois techniques complémentaires :
- **Lecture ciblée** (`Read` avec `offset`/`limit`, `Grep` pour localiser avant d'ouvrir) plutôt que `cat` du fichier entier.
- **Plan Mode** (Shift+Tab) — Claude raisonne sans pouvoir éditer, puis demande validation. On évite les itérations brouillonnes coûteuses en tokens.
- **Modèle d'effort** (cf. §2.1) — Haiku pour les passes mécaniques, Sonnet pour le code, Opus pour le refacto cross-fichiers.

## Étape 1 — Choisir le module à refactorer

Cible recommandée : **`src/components/Board.tsx`** (le fichier le plus chargé du repo après §2.9, ~137 lignes). Il mélange aujourd'hui :

1. Le **rendu canvas** (`drawGrid` + constantes de cellule).
2. La **gestion d'état** du simulator (`useState`, `useEffect` boucle, callbacks).
3. La **composition JSX** (PatternSelector + GenerationCounter + SimulatorControls + canvas).

Trois responsabilités dans un seul fichier = friction de lecture pour Claude, dérive de focus. On va les séparer.

---

## Étape 2 — Conduire la session avec `/compact`

Démarre la session avec `claude` à la racine du repo, puis prompte :

> 1. Lis `src/components/Board.tsx` et `CLAUDE.md` ciblé sur les conventions `core/`/`components/`. Pas plus.
> 2. Liste les 3 responsabilités présentes dans `Board.tsx` et propose un découpage en 3 fichiers (drawing pur / hook custom de simulation / composant de composition).
>
> Quand tu as la proposition, **stop**. Je veux vérifier le plan avant que tu touches au code.

Une fois le plan validé, lance le refactor en deux temps :

> Phase A — Extrais le drawing :
> - Crée `src/components/Board.draw.ts` qui exporte `drawGrid(canvas, grid)` + les constantes `CELL_SIZE`, `ALIVE_COLOR`, `DEAD_COLOR`, `GRID_LINE_COLOR`. Aucune dépendance React.
> - Crée son test sibling `src/components/Board.draw.test.ts` qui valide la fonction sur une grille minimale (mock `HTMLCanvasElement` via un objet avec un `getContext` qui retourne un stub de `CanvasRenderingContext2D`).
> - Importe `drawGrid` dans `Board.tsx`.

**Avant la phase B, déclenche `/compact`.** Le contexte est plein de la phase A, on n'a plus besoin du détail. Note dans ta trace ce qui a été compacté.

> Phase B — Extrais l'état :
> - Crée `src/components/use-simulator.ts` (custom hook) qui expose `{ state, handlers }` où `handlers = { onPlay, onPause, onStep, onReset, onSpeedChange, onPatternChange }`. Le hook encapsule `useState<SimulatorState>`, `useEffect` boucle d'animation, et les `useCallback`. Signature : `useSimulator({ initialGrid, initialPattern, initialSpeedMs })`.
> - Réduis `Board.tsx` à la composition pure : appel du hook + composition JSX (PatternSelector / GenerationCounter / SimulatorControls / canvas). Objectif : **< 70 lignes**.
> - Les 11 tests existants doivent toujours passer (le moteur `core/` n'est pas touché).

## Étape 3 — Tracer la démarche

Crée `docs/refactors/3.1-compact-session.md`. Le fichier documente la session :

- **Module refactoré** : `src/components/Board.tsx`.
- **Avant** : 137 lignes, 3 responsabilités mêlées (drawing + state + composition).
- **Après** : ~50 lignes (composition), `Board.draw.ts` (~40 lignes, pur), `use-simulator.ts` (~50 lignes, hook).
- **Conduite de session** : quand tu as `/compact`-é (entre phase A et phase B), pourquoi (libérer le contexte avant un gros bloc d'extraction), ce que tu as gardé en mémoire (le contrat des fonctions à extraire), ce qui a été résumé (les détails d'implémentation de la phase A déjà mergés).
- **Mesure** : nombre de fichiers avant/après, lignes/fichier, dépendances entre modules.

Ce document est **la trace observable** demandée par le check. Sans lui, pas de validation §3.1.

## Étape 4 — Vérifier

```bash
npm test               # 11 tests verts + tests Board.draw (3-4 cas)
npm run check:3.1      # vert : trace + extraits + Board.tsx allégé
npm run check          # 11/15 ✅ (1.4 → 3.1)
npm run dev            # comportement inchangé : Play anime la grille
```

Si `check:3.1` rouge :

- `Trace absente` : `docs/refactors/3.1-compact-session.md` manque ou est vide.
- `Board.draw.ts manquant` : extraction du drawing pas faite.
- `use-simulator.ts manquant` : extraction du hook pas faite.
- `Board.tsx trop long` : composition pas assez allégée (> 70 lignes).
- `Test Board.draw absent` : sibling test du module pur extrait manquant.
